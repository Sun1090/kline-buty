## 一、个人自动化的合规边界

不同市场对个人程序化交易的态度差异极大，先摆事实（**政策细节以最新监管规定为准**）：

| 市场 | 现状 | 个人量化空间 |
|---|---|---|
| A 股 | 程序化交易纳入监管：2023 年起逐步落地报备制度（沪深北交易所发布程序化交易管理细则），对高频/异常交易有重点监控 | 合规成本高；且券商对个人基本不开放量化下单接口 |
| 期货 | 程序化交易合规常见，但需通过期货公司报备，有撤单率/申报笔数等监控指标 | 个人通过期货公司 API（如 CTP）可行，门槛与门槛资金较高 |
| 加密现货/合约 | 无统一监管门槛，各交易所自定 API 政策与风控 | 个人最容易跑通，但要注意各平台条款与地区限制 |
| 境外券商 | 盈透等提供官方 API，但接口文档、合规申报面向机构为主，个人可用但需自行确认条款 | 有一定门槛，且涉及跨境资金合规 |

### 1.1 A 股程序化交易监管要点

- 2023 年 9 月沪深北交易所发布程序化交易管理实施细则（征求意见稿/落地稿），核心：**程序化交易报备、账户资金规模申报、异常交易行为监控**（频繁报撤单、瞬时大单、自成交等）；
- 2024 年进一步落地《证券市场程序化交易管理规定（试行）》等规则，程序化交易投资者需按交易所与券商要求报备；
- 个人即使通过间接方式自动化交易，只要被识别为程序化交易，同样适用监控与报备要求。
- **以上为概括性提示，具体报备范围、标准以沪深北交易所与证监会最新公告为准。**

### 1.2 加密平台的风控

加密交易无监管门槛，但**<mark>平台侧风控是硬约束</mark>**：

::: warning 🛑 API Key 权限红线
只开**交易 + 只读**，**绝不开提现权限**——即使被盗也无法划走资产。
:::

- 高频调接口会被风控限频甚至封禁 API；
- 部分平台（如 Binance）对特定地区的个人访问有服务条款限制，**使用前确认你所在司法辖区的规定**。

### 1.3 境外券商 API

::: info 📖 境外券商 API 说明
盈透证券（Interactive Brokers）提供官方 API（TWS API），可做程序化交易，但接口以桌面客户端 TWS 为载体，要求程序常驻运行；美股/港股的报单频率、模式（IBKR 也有限频与风控）均需按其文档执行。涉及出入金与税务，务必自行完成合规确认。
:::

## 二、加密量化自动化实战

本节以 Binance 现货为例（OKX/Bybit 思路一致，字段与限频以各自官方文档为准）。

### 2.1 API Key 创建与权限设置

1. 登录交易所后台 → API 管理 → 创建 API Key；
2. 权限只勾 **现货交易** 与 **读取**，**不要勾选提现**（即使被盗也无法划走资产）；
3. 启用 IP 白名单（只放行你 VPS 的固定 IP）；
4. 保存 Key 与 Secret 到本机环境变量，**不要写进代码/提交 git**。

```bash
export BINANCE_API_KEY="xxxx"
export BINANCE_API_SECRET="xxxx"
```

### 2.2 下单示例

使用官方维护的 `binance-connector`（`pip install binance-connector`），示例代码仅教学用，实盘风险自负：

```python
import os
from binance.spot import Spot

client = Spot(
    api_key=os.environ["BINANCE_API_KEY"],
    api_secret=os.environ["BINANCE_API_SECRET"],
)

# 查询现货账户（key 必须有读取权限）
acct = client.account()
usdt = [b for b in acct["balances"] if b["asset"] == "USDT"][0]
print("可用 USDT:", usdt["free"])

# 下单前先查交易对过滤规则（最小下单量、步长）—— 不查必踩坑
info = client.exchange_info(symbol="BTCUSDT")
print(info["symbols"][0]["filters"])

# 市价买入（示例数量，实盘务必按过滤器规则校验）
order = client.new_order(
    symbol="BTCUSDT",
    side="BUY",
    type="MARKET",
    quantity="0.001",
)
print("订单号:", order["orderId"])
```

### 2.3 限频与权重

- 交易接口按权重计费，权重耗尽返回 429/418；被限频后必须**指数退避**（等 1s→5s→30s→120s）重试；
- 下单请求务必做**幂等保护**：本地生成唯一 `newClientOrderId`，重试用同一 ID，避免网络抖动导致重复下单；
- 每小时对一次本地持仓与交易所账户（对账），差额即漏单/重复单信号。

### 2.4 WebSocket 订阅行情

实时行情用 WebSocket 而不是轮询 REST（省权重、延迟低）。示例代码仅教学用：

```python
import json
import time
import websocket

def on_message(ws, message):
    data = json.loads(message)
    k = data.get("k")
    if k and k["x"]:                       # k["x"]=True 表示该 K 线收盘
        print("K线收盘:", k["s"], k["t"], "close =", k["c"])

def on_open(ws):
    ws.send(json.dumps({
        "method": "SUBSCRIBE",
        "params": ["btcusdt@kline_1m"],
        "id": 1,
    }))

def on_close(ws, *args):
    print("连接断开，3 秒后重连")
    time.sleep(3)
    ws.run_forever()

ws = websocket.WebSocketApp(
    "wss://stream.binance.com:9443/ws",    # 以官方文档为准
    on_message=on_message, on_open=on_open, on_close=on_close,
)
ws.run_forever()
```

::: warning ⚠️ 断线重连的正确姿势
上面是最简演示，生产脚本应做成循环 + 指数退避 + 心跳检查（N 秒无消息视为死链主动重连），并在重连后**<mark>拉一次 REST 快照补齐缺口</mark>**，避免行情缺口导致信号错乱。
:::

### 2.5 服务器运行：VPS 部署与日志

个人自动化的常驻环境用云服务器（VPS），要点：

| 事项 | 建议 |
|---|---|
| 系统 | Ubuntu LTS，低配（2C2G）足够日线级策略 |
| 部署 | 代码放服务器 + `systemd` 托管（`Restart=always`），不要裸跑 nohup |
| 日志 | 全部落盘 `logs/`，按天切分；成交回报、错误、异常各一类 |
| 监控 | 心跳上报（失败即告警推送 Telegram/钉钉），见第五节 |
| 时区 | 服务器统一 UTC，脚本内转换，别依赖服务器本地时区 |
| 密钥 | Key 放 `~/.env`（权限 600），systemd 用 `EnvironmentFile` 注入，不写进代码 |

## 三、A 股自动化现状：讲清楚现实与风险

个人在 A 股做自动化，现实的困境是**接口关上了**：

1. 券商标准交易通道不对个人开放 API；个别券商有「程序化交易」通道但面向机构与合格投资者，且需报备；
2. 「外挂式」方案（模拟点击、内存注入、抓包重放）普遍违反券商协议、有封号与合规风险，部分行为可能触及证券法禁止条款，**不建议以任何方式尝试**；
3. 2023 年以来的程序化交易监管进一步收紧了非报备自动化的空间；
4. 合规的正路：量化交易需报备（以最新监管规定为准），个人门槛高 → 现实是多数个人先走「信号 + 人工下单」。

::: tip 💡 结论
A 股个人自动化，现阶段请把期望放在「**<mark>半自动</mark>**」上——机器负责研究、计算、提醒，人负责执行。既合规，又避开接口黑洞。
:::

## 四、「半自动」路线：信号提醒 + 人工下单

信号推送是个人量化的高性价比形态：策略算好买卖点，把结论推到手机，你确认后人工下单。示例代码仅教学用，实盘风险自负。

### 4.1 Telegram Bot 推送

```python
import requests

def send_telegram(text: str, bot_token: str, chat_id: str):
    url = f"https://api.telegram.org/bot{bot_token}/sendMessage"
    requests.post(url, json={"chat_id": chat_id, "text": text}, timeout=10)

# 例：每日 15:05 推送当日信号
send_telegram("BTC 日线：突破 20 日均线，建议买入 0.01 BTC（人工确认）",
              bot_token="你的bot_token", chat_id="你的chat_id")
```

### 4.2 钉钉群机器人推送

```python
import base64
import hashlib
import hmac
import time
import urllib.parse
import requests

def send_ding(text: str, webhook: str, secret: str):
    ts = str(round(time.time() * 1000))
    sign = urllib.parse.quote_plus(base64.b64encode(
        hmac.new(secret.encode(), f"{ts}\n{secret}".encode(), hashlib.sha256
        ).digest()))
    url = f"{webhook}&timestamp={ts}&sign={sign}"   # 加签方式以钉钉官方文档为准
    requests.post(url, json={"msgtype": "text", "text": {"content": text}}, timeout=10)
```

- 推送里必须带**上下文**：标的、方向、建议数量、触发时间、策略名——半夜醒来看不懂的告警等于没有告警；
- 任何信号都不建议「无脑照做」：推送是辅助，决策是人。

## 五、实盘注意事项清单

| 事项 | 具体做法 |
|---|---|
| 小资金起步 | 实盘第一笔只放「亏光也不影响生活」的钱；策略稳定 3 个月以上再加仓 |
| 监控告警 | 程序崩溃、信号异常、订单失败、净值**<mark>回撤</mark>**超阈值都要推送；「无人值守」前提是「有告警」 |
| 双因子保护 | 关键操作（清仓、提现）人工二次确认；持仓上限、单日亏损上限写死在代码里且不可被策略覆盖 |
| 密钥安全 | Key 仅存环境变量/权限 600 文件；**开 IP 白名单、不开提现权限**；真实泄露事故：某量化群流传的泄露 Key 被脚本在数分钟内清空余额，盗币者对全网扫描 `git` 中的 Secret 是常规操作——密钥进过 git 历史就视为已泄露，立即吊销重建 |
| 对账 | 每日脚本对比本地持仓 vs 交易所持仓，差额报警 |
| 数据源冗余 | 行情至少两个独立源，A 源断流切 B 源，别在错误行情上下单 |

---

::: danger 💀 亏钱策略自动化后亏得更快更均匀
**自动化解决的是执行纪律，不是策略有效性——亏钱策略自动化后亏得更快更均匀。** 价值顺序是：策略有效（最大难点）→ 执行可靠（工程难点）→ 自动化（锦上添花），不要搞反。
:::

## 六、「自动化 ≠ 自动赚钱」

最后一条，也是最重要的一条：

- 自动化解决的是**<mark>执行纪律</mark>**，不是**<mark>策略有效性</mark>**——亏钱策略自动化后亏得更快更均匀；
- 回测到实盘的落差是常态：**<mark>滑点</mark>**、限频、断线、接口变动、平台规则变化，都会吃掉回测利润；
- 真正的价值顺序：**策略有效（最大难点）→ 执行可靠（工程难点）→ 自动化（锦上添花）**。不要搞反。
- 加密现货 7×24 交易 + 自动下单，意味着你不在场时系统也在替你承担风险——请先问自己：这套代码在没有我的任何干预下运行一周，我睡得着吗？
